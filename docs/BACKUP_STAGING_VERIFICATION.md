# BACKUP-01 / P1 — проверка подготовленного staging-каталога

`verify_staged_restore(plan, staging)` — отдельная headless read-only
проверка содержимого **уже подготовленного** скрытого каталога. Каталог должен
находиться рядом с отсутствующим назначением и иметь префикс
`.geolog-restore-`. Список подпапок и файлов должен в точности совпадать
с `BackupRestorePlan`; посторонние, пропавшие и символьные пути запрещены.

Для каждого файла сверяются размер, SHA-256 и идентичность объекта до и
после чтения; также повторно проверяются идентичности каталогов и их состав.
В случае несоответствия вызывается `BackupError`, без записи, удаления или
публикации. Покрыты регрессиями подмена файла во время хеширования,
появление постороннего файла, повреждение, пропуски, коллизии и symlink.

**Не готово:** автоматическая очистка после аварийного завершения, перенос записи из
`ManualBackupService.restore` в staging, интеграция с атомарной
no-replace публикацией и Windows field acceptance. Старый `restore`
остаётся неизменным и не является crash-atomic. Проверка по именам и
идентичностям не блокирует внешние процессы: существует TOCTOU-окно
между проверкой и будущей публикацией. На Windows отсутствие
`O_NOFOLLOW` дополнительно не даёт атомарного запрета следования
символическим ссылкам при открытии, хотя тип и идентичность проверяются.

Исходные LAS/WITS/ГТИ, геологические расчёты, GUI и обязательные Windows
Release Gate не изменены. Qt #544 и физическая печать не закрыты.

## Отдельная подготовка staging (P1)

`prepare_staged_restore(plan, max_total_bytes=...)` повторно вызывает
`plan_restore` и требует полного совпадения с показанным планом. Затем
создаёт уникальный скрытый каталог `.geolog-restore-*` рядом с отсутствующей
целью, потоково переносит разрешённые ZIP entries, сверяет размеры/SHA-256,
вызывает `fsync` для файлов и проверяет исходный ZIP и готовый staging через
`verify_staged_restore`. Возвращает путь только после успешной проверки.

При обрабатываемой ошибке удаляются только ещё идентичные созданные этим
вызовом файлы и пустые каталоги; чужая замена остаётся на диске. Успешный
staging **не публикуется** и остаётся ответственностью вызывающего кода.
Никакая фоновая очистка или интеграция с `ManualBackupService.restore`
не включена. Сбой питания/процесса может оставить staging; проверка
`fsync` файлов не доказывает durability каталогов. Внешние писатели не
блокируются, проверки идентичности и cleanup имеют TOCTOU-окна.
Физическая Windows-приёмка и Qt #544 не закрыты.
