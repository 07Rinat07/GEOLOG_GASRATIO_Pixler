# Правила документации

## Канонические документы

- `docs/PROJECT_PLAN.md` — единственный план.
- `docs/CHANGELOG.md` — единственная история изменений.
- `docs/ARCHITECTURE.md` и `docs/REQUIREMENTS.md` — инженерные контракты.
- `docs/TESTING.md` — единственный общий quality/release gate; предметные field/interoperability
  checklists допустимы как его входы.
- `docs/{ru,kk,en}` — актуальные пользовательские, операторские и локализованные инженерные
  инструкции с одинаковым набором имён.

Запрещены отдельные `RELEASE_NOTES_*`, `BUILD_MANIFEST_*`, `HOTFIX_REPORT_*`,
`IMPLEMENTATION_REPORT_*`, `INCREMENT_*`, дополнительные `*_PLAN.md`, AI-аудиты и копии
статуса проекта. Generated test results, screenshots, preview и build manifests хранятся вне Git
(как CI artifacts после появления CI), а не в `docs`.

## Обновление

При изменении поведения одновременно обновляются:

1. код и regression test;
2. соответствующая инструкция RU/KK/EN;
3. `ARCHITECTURE.md` или `REQUIREMENTS.md`, если изменился контракт;
4. `PROJECT_PLAN.md`, когда меняется статус, объём, приоритет, зависимость,
   критерий приёмки или номер PR задачи (план → разработка → проверка → интеграция);
   без копирования результатов временных запусков CI;
5. краткая запись в `CHANGELOG.md`;
6. `SECURITY.md` и локализованные security guides при изменении импорта, сети, credentials,
   resource limits или retention.

## Обязательная синхронизация каждой разработки

- Один план `docs/PROJECT_PLAN.md` остаётся единственным источником решений и открытой
  очереди; `docs/CHANGELOG.md` фиксирует **прошедшие merge** изменения и явно
  помеченные работы «на проверке». Не создавать второй roadmap или локальные копии плана.
- До открытия PR инженер сверяет существующие возможности и backlog, не создаёт
  дублирующие модули, отмечает scope и реальный статус задачи и обновляет
  соответствующие инженерные контракты / источники расчётных методик.
- **Любое изменение интерфейса, назначения показателей, расчётного поведения,
  действий оператора, импорта/экспорта или отчёта** требует согласованных инструкций
  в `docs/ru`, `docs/kk`, `docs/en` в том же PR; обновляются существующие
  тематические руководства, а не отдельные файлы «на одну версию».
- Пользовательские инструкции должны содержать те же реальные команды, входы,
  ограничения, смысл показателей и примеры на всех трёх языках. Не утверждать,
  что работающая функция доступна в интерфейсе, если реализован только data-only API.
  Не переводить значения проб, мнемоники и оригинальный пользовательский текст.
- Если изменились формулы, их исходные параметры или смысл поля LAS, сохранять
  версию/источник методики, совместимость файлов и воспроизводимые регрессии;
  обновлять объяснение в трёх локализациях без выдуманных региональных порогов.
- **Критерий готовности PR:** код и тесты, план (при изменении статуса/объёма),
  инженерный контракт при его изменении, changelog и все затронутые
  RU/KK/EN инструкции проверены вместе. Проверки синхронизации документов,
  переводов, ссылок и три обязательных Windows gate не отключаются.
- Статус **«завершено»** ставится только после фактического слияния, успешного
  контрольного gate на обновлённом `main` и выполнения заявленных критериев.
  Завершённые программные tests не подменяют полевую/методическую валидацию.

Корневой и локализованные README используют одну команду запуска:
`python -m geoworkbench.app.main`.

## Защита данных

- Project, LAS, WITS/WITSML captures, exports, diagnostics и local paths являются
  пользовательскими данными и не попадают в Git.
- Разрешённый fixture должен находиться в `tests/fixtures` или контролируемом `resources/samples`,
  быть синтетическим/обезличенным и иметь понятное назначение.
- В документации не публикуются реальные имена скважин, клиентов, локальные пути и credentials.

## Проверка документации

Для документационных изменений выполняются:

```powershell
python tools/check_documentation.py
python -m pytest -q tests/test_documentation_sync_0762.py
```

Проверка контролирует одинаковые RU/KK/EN-файлы, рабочие ссылки, достижимость каждого документа
из канонического индекса, i18n keys, runtime marker, единственный план, отсутствие исторических
отчётов и каноническую команду запуска. Полный gate определён в [TESTING.md](TESTING.md).
