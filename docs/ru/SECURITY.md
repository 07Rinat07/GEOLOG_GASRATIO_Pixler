# Безопасная работа с приложением

Эта инструкция предназначена для пользователей и администраторов GEOLOG GASRATIO@Pixler.
Приложение является инструментом поддержки решений, а не системой well control или аварийной
защиты. Используйте корпоративные правила доступа, резервного копирования и обращения с
геологическими данными вместе с рекомендациями ниже.

На 28 июля 2026 года открыт **P0 repository incident**: `project.geolog.json` и пять
LAS-related sidecars удалены из текущего Git-индекса и защищены правилами `.gitignore`, но ранее
опубликованная public history всё ещё может содержать около 31,8 MB материалов, похожих на
реальные скважинные данные, и локальные абсолютные пути. До решения владельца данных и очистки
истории не клонируйте, не зеркалируйте и не распространяйте эти artifacts.

## Перед открытием и импортом

Считайте LAS, GS2/Paradox, WITSML XML/ZIP/EPC, проекты, формы, SVG и изображения недоверенными,
пока их источник не подтверждён.

1. Работайте с копией и сохраните fingerprint/SHA-256, если отправитель его предоставил.
2. Принимайте файл только от известного контрагента и проверьте ожидаемый тип и размер.
3. Откройте Import Review, проверьте скважину, индекс, мнемоники, UOM, NULL, предупреждения и
   число строк до commit.
4. Отмените импорт, если архив неожиданно велик, содержит неизвестные пути, запрашивает сеть,
   показывает DTD/entity/external-reference error или меняет больше объектов, чем ожидалось.
5. Не включайте macros/scripts и не переходите по внешним ссылкам из импортированного содержимого.

Успешный parser не доказывает корректность данных. Сверьте критические каналы и интервалы с
исходным отчётом. Экспорт создаёт отдельный файл и не заменяет **Ctrl+S** для проекта.

## WITS0: только локальная или изолированная сеть

WITS Level 0 не предоставляет встроенные шифрование и аутентификацию.

- Оставляйте адрес TCP-сервера `127.0.0.1` по умолчанию, если GSWITS работает на том же компьютере.
- Для отдельного компьютера указывайте конкретный адрес доверенного интерфейса.
- `0.0.0.0` используйте только после явного согласования в физически или логически изолированной
  доверенной сети с firewall allowlist.
- Никогда не открывайте WITS0-порт в интернет, не настраивайте public cloud listener или
  router port forwarding.
- Перед полевым запуском подтвердите IP/порт, владельца источника, каталог raw, свободное место
  и план остановки/recovery.

Если обнаружено неизвестное подключение, остановите capture, сохраните журнал и raw-сегменты,
изолируйте интерфейс и сообщите администратору. Не удаляйте evidence до triage.

## Удалённые WITSML и ETP

- Удалённый WITSML SOAP разрешён только по **HTTPS**, ETP — только по **WSS**, с включённой
  проверкой сертификата и имени хоста.
- Ошибка сертификата, истёкший срок или неожиданное имя хоста — причина остановиться, а не
  отключать verification.
- HTTP/WS или отключённая проверка допустимы только для loopback (`127.0.0.1`/`localhost`) и
  контролируемых тестовых fixtures.
- Redirects не выполняются. Проверьте окончательный endpoint у администратора; не переносите
  credentials на другой URL вручную.
- Используйте read-only учётную запись с минимальными правами и ожидаемыми Well/Wellbore.
  Ограничивайте время, объём ответа и число повторов.

Не подключайтесь к endpoint, полученному из неизвестного проекта, письма или diagnostic bundle,
пока владелец сервера не подтвердит его отдельным доверенным каналом.

## Credentials и secrets

Пароли и tokens сохраняйте через системный credential store; на Windows используется Windows
Credential Manager.

- не помещайте пароль в URL, имя профиля, project file, комментарий, screenshot или тикет;
- не используйте один credential для test и production;
- удаляйте неиспользуемую запись из credential store и отзывайте доступ на сервере;
- при подозрении на утечку остановите удалённое подключение, смените secret и сообщите
  администратору;
- перед передачей project file проверьте, что получателю отдельно выданы только необходимые права.

Удаление профиля подключения не обязательно удаляет системный credential; проверьте credential
store отдельно.

## Diagnostics и приватность

Логи и diagnostic bundles могут содержать локальные пути, имена пользователей, адреса серверов,
идентификаторы скважин, мнемоники и фрагменты измерений, даже если пароль исключён.

1. Соберите минимальный интервал и воспроизведите проблему на обезличенной копии, если возможно.
2. Просмотрите каждый файл перед отправкой; удалите credentials, tokens, персональные данные,
   коммерческие названия и не относящиеся к проблеме raw values.
3. Не редактируйте исходное evidence на месте: храните защищённый оригинал и создайте отдельную
   очищенную копию с отмеченными изменениями.
4. Передавайте архив только по одобренному защищённому каналу и только указанным получателям.
5. После закрытия обращения удалите временные копии по принятой retention policy.

Raw WITS0, GS2 и полные проекты отправляйте только с разрешения владельца данных. Для обычного
отчёта предпочтительны версия, время UTC, минимальные шаги, sanitized log и hashes.

## Сообщение об уязвимости или инциденте

Используйте частный security-канал, указанный поставщиком сборки или администратором вашей
организации. Если отдельный адрес ещё не опубликован, обратитесь к ответственному сопровождающему
приватно; не угадывайте email и не публикуйте exploit, credentials, реальные raw-данные или
неисправленный vulnerability report в открытом issue.

Включите:

- package version, ОС и способ установки;
- краткое влияние и затронутую границу: import, project, WITS0, WITSML/ETP, export или update;
- минимальные воспроизводимые шаги и безопасный synthetic fixture;
- sanitized diagnostics, UTC-время и hashes artifacts;
- сведения о возможной компрометации credentials без самих secret values.

При активном инциденте сначала остановите внешние соединения и сохраните read-only evidence.
Не продолжайте тестирование на production-сервере без разрешения владельца.

Для известного repository incident сопровождающий и владелец данных должны:

1. классифицировать данные, exposure window, affected commits/clones/releases и обязательства
   уведомления;
2. немедленно ограничить доступ или перевести remote в private на время triage;
3. только после явного разрешения удалить текущие artifacts, добавить точные `.gitignore` rules
   и переписать всю затронутую Git history;
4. запросить purge remote caches, forks, mirrors, CI artifacts и release archives и проверить
   доступные копии;
5. заменить реальные материалы минимальными synthetic fixtures с явной provenance.

Удаление файлов только из HEAD недостаточно: предыдущие commits и внешние копии продолжают
раскрывать содержимое. Не выполняйте history rewrite или удаление evidence без согласования с
владельцем данных и ответственным за incident response.

## Контрольный список перед полевым запуском

- известный repository incident классифицирован, remote ограничен, а реальные fixtures не
  попадают в новые commits;
- источник файлов и сетевой peer подтверждены;
- WITS0 остаётся на loopback или в изолированной allowlisted сети;
- удалённые WITSML/ETP используют verified HTTPS/WSS без redirects;
- credentials находятся только в системном store и имеют минимальные права;
- raw/project каталоги защищены, свободное место и backup проверены;
- diagnostic sharing и incident contacts согласованы;
- после настройки выполнены test capture, controlled close, **Ctrl+S** и повторное открытие.
